# WP-2.2 `plugin-sdk-py` — handoff

## What was built

The Python plugin SDK distribution `atomc-plugin-sdk` at `packages/plugin-sdk/python/`
(hatchling, `src/atomc_plugin_sdk`, `py.typed`):

- **`manifest.py`** — `load_manifest(source)` / `validate_manifest(data) -> PluginManifest`.
  Ordered validation: (1) `manifest_version` support check with a clear `/manifest_version` error,
  (2) Draft 2020-12 validation against the shared WP-2.1 schema, (3) strict Pydantic parsing, then
  (4) the cross-field rules a JSON Schema cannot express. Errors are path-oriented
  (`ManifestError(path, message, validator)`).
- **`schema.py`** — locates the shared schema (`ATOMC_PLUGIN_SCHEMA` → walk-up to
  `packages/plugin-sdk/schema/atomc-plugin.schema.json` → packaged `_schema/` fallback) and
  validates with Draft 2020-12 (`jsonschema`). **No second schema is authored or committed.**
- **`plugin.py`** — `@atomc_plugin(manifest=...)` decorator (class / factory / instance) attaching
  `__atomc_manifest__` (and optional `__atomc_handlers__`); `define_plugin(...) -> PluginDefinition`;
  `AtomcPlugin`/`PluginHost` protocols. Eager manifest validation, no plugin import-time side effects.
- **`host.py`** — structural `PluginHost` protocol (`ir_get`, `ir_transact(path, base_rev, ops,
  holder)` with ops relative to `path`, `artifact_root`, `logger`, `cache`, `events`) plus
  `IrSnapshot`/`TransactResult`/`JsonPatchOp`/`LoggerLike`/`CacheLike`/`EventSink`. No daemon imports.
- **`conformance.py`** — `conformance(plugin) -> ConformanceReport` and `assert_conformance(plugin)`;
  validates the manifest, checks every declared handler exists and is callable, rejects
  registered-but-undeclared handlers, duplicate declarations, invalid `produces` scopes and
  malformed tool/gate definitions. Structured `ConformanceFinding`s or `PluginConformanceError`.
- **`testing.py`** — `FakePluginHost` for daemon-free unit tests.
- **`README-python.md`** at `packages/plugin-sdk/README-python.md` — authoring guide.

## Integration fix (daemon adapter) — separate branch

The daemon (WP-2.3) prefers the SDK's `validate_manifest` when installed. Two gaps were fixed on
`wp/2.2-daemon-sdk-adapter` (based on `origin/wp/2.3-daemon-core` @ `8ebf006`; commit `9173750`),
because the daemon package does not exist on this SDK branch:

- Coerce the SDK `PluginManifest` back to the daemon's local `Manifest` via
  `model_dump(mode="python")` (WP-2.3 had already landed the coercion).
- **Translate `atomc_plugin_sdk.errors.ManifestValidationError` into
  `atomcd.plugins.manifest.ManifestError`** with path-oriented `errors` — previously invalid
  manifests leaked the SDK exception type (the 13 daemon failures).
- Added `test_installed_sdk_manifest_errors_become_daemon_errors` (skips when the SDK is absent;
  fails against the unpatched adapter).

Verified with `atomc-plugin-sdk` on `PYTHONPATH`: full daemon suite **127 passed** (was 13 failures),
daemon `ruff`/`format` clean, `mypy --strict` clean (22 files); SDK suite still 93 passed.

## Schema-vs-model audit (no invented differences)

The generated schema is the single structural authority; the Python code was reviewed against it
and **relaxed** everywhere it had been stricter, so Python never rejects a schema-valid manifest:

| Field | Shared-schema rule | Python before | Python now |
|---|---|---|---|
| `name` | `^[a-z0-9]+(?:-[a-z0-9]+)*$` (leading digit allowed) | required leading letter + banned `plugin-` prefix | deferred to schema |
| `version` | schema SemVer pattern (allows `1.0.0-01`) | stricter semver.org regex | deferred to schema |
| `runtime.python` | `^[A-Za-z_][A-Za-z0-9_.]*:[A-Za-z_$][A-Za-z0-9_$]*$` | stricter regex (no `$`) | deferred to schema |
| `watches[].ir[]` | pointer pattern allows `""` | required non-empty `/`-prefixed | deferred to schema |
| `tools[].input_schema` | JSON Schema object **or** boolean | object only | `dict[str, Any] \| bool` |
| `produces`, gate ids, `after`, UI entry | schema patterns | duplicated hand-rolled checks | deferred to schema |

Cross-field rules kept in Python (not expressible in the generated schema): uniqueness of
`watches[].id`, `gates[].id`, `tools[].name`, `cli[].command`, `ui[].panel`, unique `produces`;
and mutating tools require at least one `produces` write scope. `tests/test_schema_alignment.py`
asserts Python accepts exactly what the schema accepts (and rejects what it rejects) for the edge
cases above.

## Design decisions

- **Schema is authoritative.** Structural validation runs the shared JSON Schema; Pydantic only
  parses typed models afterwards. Cross-field checks that Zod refinements do not emit to JSON Schema
  are re-applied in Python. This avoids a competing schema and any drift.
- **`manifest_version` checked before schema validation** for one clear `/manifest_version` error.
- **Lenient Pydantic defaults** for nested optional fields so the SDK never rejects a schema-valid
  document.
- **No `atomc-core-ir` dependency.** `PluginHost` uses local structural types; the daemon satisfies
  the protocol without an import cycle.
- **Factory invocation during conformance** is intentional (mirrors TS setup); exceptions become a
  `FACTORY_ERROR` finding.
- **`jsonschema` 4.26** Draft 2020-12 rather than hand-rolled validation.

## Deviations from contract

None in code. One **contract-prose vs generated-schema gap**: `plugin-manifest.md` says `name` has
"no `plugin-` prefix", but the frozen generated schema (`^[a-z0-9]+(?:-[a-z0-9]+)*$`) permits a
`plugin-` prefix, so the Python SDK permits it to stay byte-aligned with the TypeScript SDK. See
Open issues.

## Open issues

- **`name` prefix gap** (above). Resolving it requires a Zod-schema change in WP-2.1 plus a
  regenerated artifact; this SDK then inherits it automatically.
- `jsonschema` ships no type stubs, so `schema.py` carries two targeted
  `# type: ignore[import-untyped]` comments. Adding `types-jsonschema` to the root dev dependency
  group would remove them (optional).
- No shared manifest-fixture directory with WP-2.1 (no mutually owned path); each suite keeps its
  own fixtures. A future orchestrator-owned `packages/plugin-sdk/fixtures/` would let both runners
  consume identical files.
